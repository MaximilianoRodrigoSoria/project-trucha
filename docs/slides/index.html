project-trucha

Un toolkit colaborativo y open source para dar a los agentes de código memoria persistente sobre un codebase local. Esto es qué vamos a construir y qué decisiones vamos a tomar.

Hecho con 🐟 por Maximiliano Soria, Gerardo y Gerald 🤖
01 · El problema

Un agente sin memoria arranca de cero

Cada sesión reindexa

Vuelve a escanear el repo entero para responder lo que ya sabía ayer.

Pierde el contexto

Las decisiones, convenciones y notas de sesiones previas se evaporan.

O paga la nube

La alternativa habitual es una base vectorial pesada, con latencia de red y estado propio.

Necesitamos memoria local, rápida y portable que el agente pueda consultar en milisegundos.

02 · Qué vamos a construir

Un índice persistente del codebase, consultable por el agente

Indexado del repo

Recorrer, trocear (por archivo / símbolo / bloque) y persistir el contenido.

Búsqueda híbrida

Léxica (BM25, exacta) + semántica (vectorial) fusionadas en una sola respuesta.

Memoria de decisiones

Guardar notas y ADRs asociados al código y recuperarlos por contexto.

Reindex incremental

Detectar cambios por hash / mtime y actualizar sólo lo que cambió.

Interfaz para agentes

CLI + API y, más adelante, un servidor MCP para consumo directo.

Local-first

Todo en la máquina del dev: pip install y listo, sin servicios obligatorios.

03 · Arquitectura tentativa

Un pipeline con la persistencia desacoplada

ingest→ embed→ store ⟵ decisión→ retrieve→ interface

Las capas dependen de store a través de una interfaz estable, no de una implementación concreta. Así podemos comparar (y hasta cambiar) el backend sin reescribir el resto mientras la decisión sigue abierta.

CONTRATO ESTABLE = DECISIÓN REVERSIBLE
04 · Filosofía

Por qué la trucha

  • Nada contracorriente.Local-first, contra el reflejo de "todo a la nube".
  • Vive en aguas claras.Bioindicador: el índice refleja la salud real del codebase; contexto limpio y fresco.
  • Tiene memoria de retorno.El agente "vuelve a casa" al contexto acumulado en vez de empezar de cero.
  • Ágil y liviana.Baja fricción, baja latencia: entra y sale del bucle del agente en milisegundos.
  • Quiere a su trucho.Proyecto colaborativo — se construye de a muchos.

06 · Otras decisiones a tomar

El mapa de decisiones por delante

Estrategia de chunking

¿Por archivo, por símbolo (AST) o por bloque de tokens? Impacta recall y costo.

Modelo de embeddings

Local vs API; dimensión, costo, calidad. ¿Configurable / pluggable?

Ranking híbrido

Cómo fusionar léxico + vectorial (p. ej. reciprocal rank fusion) y sus pesos.

Reindex incremental

Hash vs mtime; granularidad y disparadores del re-scan.

Interfaz / protocolo

CLI, API y servidor MCP: qué contrato exponemos al agente.

Umbral de escala

A partir de qué volumen conviene migrar a un backend con servidor.

07 · Roadmap

De la decisión al toolkit

  • Fase 0 — Decisión (actual) Cerrar el backend (ADR-0001) y congelar la interfaz de store.
  • Fase 1 — Núcleo Indexado + búsqueda léxica + reindex incremental.
  • Fase 2 — Semántica Embeddings + búsqueda vectorial + fusión híbrida.
  • Fase 3 — Memoria de decisiones Persistir y recuperar notas / ADRs por contexto.
  • Fase 4 — Interfaz para agentes CLI estable + servidor MCP.
  • Fase 5 — Escala Camino de migración a backend con servidor.
